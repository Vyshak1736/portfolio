Webhook Ledger

A Django backend demonstrating signed webhook ingestion, durable event acceptance, idempotent payment records, and bounded recovery after transient failures.

The problem

Payment providers may deliver an event repeatedly or while a downstream operation is failing. This project demonstrates how to accept events durably and prevent duplicate local payment records.

What it does

  • Verify timestamped HMAC-SHA256 signatures over the exact body, enforce payload limits, and reject stale signatures.
  • Store unique event IDs in a durable database inbox and return HTTP 202 only after persistence.
  • Use payment-level uniqueness and transactions to prevent repeated writes and roll back partial processing.
  • Process events with a background Django management command, exponential retry delays, and a dead status after exhausted attempts.

How it works

Receive a signed event

Validate JSON, signature, timestamp, and payload size on the webhook endpoint.

Persist the inbox record

A unique event ID prevents duplicate acceptance; conflicting reuse is rejected.

Acknowledge acceptance

HTTP 202 means the event is stored, not necessarily processed.

Process transactionally

The worker locks a due event and commits the payment record and event state together.

Recover or quarantine

Retry transient failures with bounded delay; permanent conflicts or exhausted attempts become dead events.

Design decisions

  • The database is the durable inbox, so acceptance does not depend on successfully publishing to a separate message broker.
  • Event ID and payment ID solve different duplication problems: repeated delivery versus repeated business writes.
  • PostgreSQL row locking supports concurrent workers. SQLite is a convenience mode for a single worker; it does not provide the same row-locking behavior.

Current scope

Uses a custom synthetic webhook contract, not Razorpay-compatible signing. It does not initiate payments, reconcile real provider settlements, run Kafka or Celery, or call external payment APIs. Idempotency covers local database writes.

Next engineering steps: PostgreSQL concurrency tests, audited replay, tenant-specific signing secrets, metrics, and an outbox for downstream delivery.

Evidence and verification

The repository includes tests for signed ingestion, stale and invalid signatures, ID conflicts, duplicate delivery, permissions, retry recovery, retry exhaustion, and rollback. Its CI configuration targets SQLite and PostgreSQL.
